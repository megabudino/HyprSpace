WINDOW JITTER FIX - DEVELOPMENT NOTES
======================================

PROBLEM
-------
When a new window opens, it briefly appears at macOS's default position/size
before HyprSpace moves it to the correct tiled position, causing visible jitter.


WHAT WE TRIED
-------------

1. Hide in MacWindow.getOrRegister (FAILED)
   - Added hideInCorner() call after binding window to tree
   - Result: Still saw jitter
   - Root cause: Async gap between notification and hide call

2. Early hide in refreshObs - synchronous (FAILED)
   - Moved hide logic to observer callback, before any async dispatch
   - Used AX API to set position/size immediately when notification fires
   - Result: AX calls succeed (return 0) but window still appears at default position first
   - Root cause: macOS renders window BEFORE firing kAXWindowCreatedNotification
   
   The notification arrives, we successfully set position, but the first frame
   is already rendered at the default position.


RESEARCH: OTHER TILING WMs
--------------------------
- yabai: Has same flickering issue (GitHub issue #2485, Nov 2024)
- Amethyst: Likely has same issue (uses Accessibility API)

This appears to be a fundamental macOS limitation, not a HyprSpace bug.


CONCLUSION
----------
The Accessibility API cannot intercept window creation early enough to prevent
jitter. macOS renders the window before firing the notification.

This is a fundamental macOS limitation shared by ALL Accessibility-based tiling
window managers:

- yabai: Issue #2485 (Nov 2024) still OPEN, no solution
- Amethyst: Uses same Accessibility API, likely has same issue

ACCEPTED AS macOS LIMITATION - No fix possible without private APIs that may
not work cross-process anyway.
